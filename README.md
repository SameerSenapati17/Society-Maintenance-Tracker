# Society Maintenance Tracker (SocietyOS)

## Live Deployment
- **Hosted Frontend Application**: `https://<your-app-url>.vercel.app` (or `http://localhost:5173` locally)
- **Hosted Backend API**: `https://<your-api-url>.onrender.com/api` (or `http://localhost:5000/api` locally)

## Overview
Society Maintenance Tracker — branded as **SocietyOS** in the UI — is a full-stack web application for apartment societies. Residents can register, submit maintenance complaints with optional photos, track complaint status, and view notices. Administrators can manage all complaints, update status and priority, detect overdue work, publish notices, and trigger resident email notifications.

## Features
- Resident registration and JWT login.
- Role-based authorization for `resident` and `admin`.
- Resident-only access to personal complaints.
- Admin complaint filtering, search, priority updates, status lifecycle management, and operational dashboard analytics.
- Immutable complaint status history with actor, timestamp, and note.
- Configurable overdue detection using `OVERDUE_DAYS`.
- Optional complaint image upload through Multer and Cloudinary.
- Notice board with important notices pinned first.
- Nodemailer notifications for status changes and important notices.
- In-app notification center derived from recent status changes and important notices.
- Operational dashboard: needs attention, complaint trends, maintenance health score, recurring issue insights.
- **Nivara Intelligence Engine (Phase 3A)**: AI-assisted complaint triage with structured operational analysis.

## AI Intelligence (Nivara Intelligence Engine)
Nivara includes assistive AI operational capabilities designed to elevate property maintenance workflow:

### 1. AI Complaint Triage
- **Assistive Operational Triage**: Analyzes complaint descriptions to predict maintenance categories, assess severity levels (`Low`, `Medium`, `High`, `Critical`), evaluate urgency (`Low`, `Normal`, `Urgent`, `Emergency`), and recommend dispatch priorities.
- **Structured JSON Schema**: Enforces strict enum validation against canonical property operations enums with confidence scoring and operational reasoning.
- **Human-in-the-Loop Principle**: AI never mutates ticket status, priority, or categories automatically. Predictions are stored separately in `complaint.aiTriage` and presented in an executive dashboard panel where building managers review and decide whether to apply recommendations.

### 2. Semantic Duplicate Incident Detection
- **Vector Embeddings & Cosine Similarity**: Uses Google's **Gemini Embedding 2** (`gemini-embedding-2`) to compute 768-dimensional mathematical vector embeddings of normalized complaint content (`Category: <cat>\nDescription: <desc>`). Recognizes related issues with completely different wording (e.g., *"water dripping from ceiling"* vs *"bathroom pipe leaking"*).
- **Zero Keyword Reliance**: Does not use crude keyword matching; captures true semantic intent across a 768-dimensional vector space.
- **Lazy Generation, Caching & Model Validation**: Embeddings are computed once upon analysis, stored in `complaint.aiEmbedding`, and reused across similarity comparisons. If a stored embedding was generated by a different or outdated model, it is automatically invalidated and regenerated using the current active model.
- **Threshold & Safety Controls**: Configurable similarity cutoff (`AI_DUPLICATE_THRESHOLD=0.85`) and result limits (`AI_DUPLICATE_LIMIT=5`).
- **Human-in-the-Loop Review**: Duplicates are surfaced as assistive suggestions with match confidence percentages and quick actions (`View`, `Dismiss`). Tickets are never automatically merged or modified.

### 3. Visual Intelligence, Explainable AI & Detection (Phase 4A/4B)
- **Classification Pipeline**: Dedicated FastAPI/PyTorch microservice using a Two-Stage Transfer Learning CNN (**EfficientNet-B0**) with custom property operations classification head.
- **Detection Pipeline**: YOLOv8-compatible object detection for localized component fault detection (**Elevator Door** and **Electrical Wiring** models).
- **8 Canonical Visual Classes**: `Water Leakage`, `Wall/Ceiling Damage`, `Garbage/Waste`, `Electrical Hazard`, `Broken Infrastructure`, `Lift/Door Damage`, `Parking/Road Damage`, `Other`.
- **Explainable AI (Grad-CAM)**: Generates Gradient-Weighted Class Activation Mapping (Grad-CAM) heatmaps with Nivara's restrained operational colormap (Navy → Indigo → Amber/Rose) to highlight specific image regions influencing predictions.
- **Multimodal Fusion Layer**: Safe decision layer synthesizing Gemini text triage with CNN visual classification for holistic building management insights.
- **Model Registry & Status Lifecycle**: Model metadata and versioning tracked in `models/registry.json`. Explicit status machine (`"untrained"` | `"trained"` | `"ready"` | `"failed"`) ensures no model claims production readiness without real-world training.
- **Storage Abstraction & Backward Compatibility**: Visual artifacts support both URL-based references (production) and inline Base64 (legacy records).
- **Human-in-the-Loop Feedback & Domain Adaptation**: Residents and admins can confirm or correct visual predictions (`POST /api/complaints/:id/visual-feedback`). Feedback is stored in `complaint.visualFeedback` to accumulate verified samples for future domain adaptation without automated online mutation.

### AI Architecture & Workflow

```text
                     Resident / Admin
                            │
              Complaint Text + Attached Photo
                            │
                            ▼
                 Nivara Express Backend
                            │
            ┌───────────────┴───────────────┐
            ▼                               ▼
    Gemini Text Triage              Visual Intelligence
 (gemini-3.7-flash LLM)             (ml-service / 8001)
            │                               │
            ▼                               ▼
  Category / SLA / Action         EfficientNet-B0 + YOLOv8
            │                               │
            │                       ┌───────┴───────┐
            │                       ▼               ▼
            │                 Classification    Detection
            │                 (Grad-CAM XAI)  (Bounding Boxes)
            │                       │               │
            │                       └───────┬───────┘
            │                               ▼
            │                        Visual Evidence
            │                               │
            └───────────────┬───────────────┘
                            ▼
               Multimodal Operations Synthesis
                            │
                            ▼
                   Human Building Manager
                   (Decision & Dispatch)
                            │
                            ▼
                 Human-in-the-Loop Feedback
               (POST /complaints/:id/visual-feedback)
```

- **Provider Abstraction**: Decoupled service layer in `backend/src/services/ai/` supporting Google Gemini (via `@google/genai` with `gemini-3.7-flash` and `gemini-embedding-2`), Visual Intelligence microservice, and deterministic mock providers for testing and offline environments.
- **Security & Privacy**: API keys (`GEMINI_API_KEY`) are kept strictly on the backend. Resident profiles, passwords, and sensitive metadata are stripped before AI evaluation.
- **Strict Role Security & Graceful Fallback**: The AI triage endpoint (`POST /api/admin/complaints/:id/ai-triage`), duplicate detection endpoint (`POST /api/admin/complaints/:id/find-duplicates`), and visual analysis endpoint (`POST /api/admin/complaints/:id/visual-analysis`) are strictly restricted to authenticated administrators (`403 Forbidden` for residents). Visual feedback (`POST /api/complaints/:id/visual-feedback`) is accessible to authenticated residents and admins. Provider outages or network timeouts return controlled `503` errors without disrupting core complaint submissions or lifecycle transitions.




## Tech Stack
Frontend: React, Vite, React Router, Axios, Tailwind CSS, Recharts.

Backend: Node.js, Express.js, MongoDB, Mongoose, JWT, bcrypt, Multer, Cloudinary, Nodemailer.

## Architecture
The React SPA calls the Express API with `Authorization: Bearer <token>`. Express validates JWTs, applies role middleware, persists data in MongoDB through Mongoose, uploads images to Cloudinary, and sends email through SMTP. Dashboard analytics are calculated by backend endpoints, not by the browser.

## Environment Variables
Use `.env.example` as the template.

**Core Variables**:
`PORT`, `MONGODB_URI`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `OVERDUE_DAYS`, `CLIENT_URL`, Cloudinary keys, SMTP keys.

**AI Intelligence Variables (Phase 3A & 3B)**:
- `AI_PROVIDER`: `gemini` or `mock` (default: `gemini`)
- `GEMINI_API_KEY`: API key from Google AI Studio
- `AI_MODEL`: Gemini model name (default: `gemini-3.7-flash`)
- `AI_EMBEDDING_MODEL`: Gemini embedding model name (default: `gemini-embedding-2`, 768-dim)
- `AI_DUPLICATE_THRESHOLD`: Cosine similarity cutoff for related incidents (default: `0.85`)
- `AI_DUPLICATE_LIMIT`: Maximum number of similar incidents to return (default: `5`)

## API Documentation
Auth:
- `POST /api/auth/register` public. Body: `{ name, email, password, confirmPassword }`.
- `POST /api/auth/login` public. Body: `{ email, password }`.
- `GET /api/auth/me` authenticated.

Resident complaints:
- `POST /api/complaints` resident. `multipart/form-data`: `category`, `description`, optional `photo`.
- `GET /api/complaints/my` resident.
- `GET /api/complaints/:id` authenticated. Residents can only read their own complaint.

Admin complaints & intelligence:
- `GET /api/admin/complaints` admin. Query: `category`, `status`, `priority`, `from`, `to`, `overdue`, `search`.
- `GET /api/admin/complaints/:id` admin.
- `PATCH /api/admin/complaints/:id/status` admin. Body: `{ status, note }`.
- `PATCH /api/admin/complaints/:id/priority` admin. Body: `{ priority }`.
- `POST /api/admin/complaints/:id/ai-triage` admin. Generates and stores structured operations triage.
- `POST /api/admin/complaints/:id/find-duplicates` admin. Computes cosine similarity against existing complaint embeddings.
- `POST /api/admin/complaints/:id/visual-analysis` admin. Runs Computer Vision (EfficientNet-B0) + Grad-CAM XAI on attached photo evidence.


Dashboard:
- `GET /api/admin/dashboard` admin. Query: `trendDays` (7, 30, or 90). Returns total, status counts, overdue count, needs attention, resolution metrics, health score, trends, recurring issues, recent complaints, and category/status aggregations.

Notifications:
- `GET /api/complaints/notifications` authenticated. Returns recent status-change and important-notice notifications.

Notices:
- `GET /api/notices` authenticated.
- `POST /api/admin/notices` admin. Body: `{ title, content, isImportant }`.
- `PATCH /api/admin/notices/:id` admin.
- `DELETE /api/admin/notices/:id` admin.

Responses follow:
```json
{ "success": true, "message": "Message", "data": {} }
```
Errors follow:
```json
{ "success": false, "message": "Complaint not found" }
```

## Database Schema
User: `name`, `email`, `passwordHash`, `role`, timestamps.

Complaint: `residentId`, `category`, `description`, `photoUrl`, `status`, `priority`, `isOverdue`, `resolvedAt`, timestamps, `statusHistory`.

StatusHistory: `status`, `changedBy`, `note`, `timestamp`.

Notice: `title`, `content`, `isImportant`, `createdBy`, timestamps.

## Complaint Lifecycle
Valid transitions are `Open -> In Progress`, `Open -> Resolved`, and `In Progress -> Resolved`. Once a complaint is `Resolved`, the backend rejects any further status changes.

## Overdue Detection
`OVERDUE_DAYS` controls when unresolved complaints become overdue. Resolved complaints are never overdue. The backend refreshes overdue state when listing or reading complaints and in dashboard calculations.

## Photo Upload Flow
Resident form sends `multipart/form-data` to Express. Multer validates file type and size in memory. The backend uploads the image to Cloudinary and stores only the Cloudinary URL in MongoDB.

## Notification Flow
When an admin changes complaint status, the backend saves the status history entry and sends the resident an email. When an admin creates an important notice, marks an existing notice important, or edits the title/content of an already-important notice, all resident emails are collected and notified. SMTP failures are logged and do not roll back saved data.

## Administrator Bootstrap & User Roles

- **Resident Registration**: Public registration (`/register`) automatically creates accounts with `role: "resident"`. Client-supplied role overrides are strictly ignored by the backend.
- **Administrator Account Creation**: Administrators are created securely through the backend CLI bootstrap utility:
  ```bash
  cd backend
  npm run create-admin
  ```
  The command interactively prompts for the administrator's name, email, and password, securely hashes the password with bcrypt, and provisions the `admin` role. Alternatively, `ADMIN_NAME`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD` environment variables can be provided.
- **Role-Based Access Control**: All `/api/admin/*` endpoints strictly require a valid JWT token and `role === "admin"`. Resident attempts to access admin APIs receive `403 Forbidden`.
